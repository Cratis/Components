Continue from [List the authors](./list-it.mdx), keeping the backend, providers, and table working. This chapter adds the write side with the generated `RegisterAuthor` command from `src/Authors/RegisterAuthor.ts`. The librarian supplies `name`; the dialog supplies `id`. Components binds the typed field, validates the command through Arc, and executes it when the user confirms.

## Add an author

<Steps>

1. **Build the dialog from the command.** `CommandDialog` takes the generated command, renders the fields you list plus the OK/Cancel footer, validates, and executes on confirm. The field accessor `(command) => command.name` is typed against `RegisterAuthor`:

    ```tsx title="src/AddAuthor.tsx"
    import { useState } from 'react';
    import { Guid } from '@cratis/fundamentals';
    import { CommandDialog } from '@cratis/components/CommandDialog';
    import { InputTextField } from '@cratis/components/CommandForm';
    import { RegisterAuthor } from './Authors/RegisterAuthor'; // generated proxy

    export const AddAuthor = () => {
        const [id] = useState(() => Guid.create());
        return (
            <CommandDialog<RegisterAuthor>
                command={RegisterAuthor}
                title='Add author'
                okLabel='Add'
                initialValues={{ id }}
            >
                <InputTextField<RegisterAuthor>
                    value={(command) => command.name}
                    title='Name'
                    placeholder='Sample Author'
                />
            </CommandDialog>
        );
    };
    ```

    `RegisterAuthor` requires an `id` that the librarian never types, so the dialog creates one and passes it in `initialValues`. The command is complete except for the name from the moment the dialog opens.

2. **Open it from the screen.** `useDialog` from Arc gives you a wrapper element to render and a function to show it. Add a button above the table from chapter 1:

    ```tsx title="src/Authors.tsx"
    import { useDialog } from '@cratis/arc.react/dialogs';
    import { Button, Page } from '@cratis/components/Common';
    import { Column, DataTableForObservableQuery } from '@cratis/components/DataTables';
    import { AllAuthors } from './Authors/Author';
    import { AddAuthor } from './AddAuthor';

    export const Authors = () => {
        const [AddAuthorDialog, showAddAuthor] = useDialog(AddAuthor);
        return (
            <Page title='Authors' showTitle>
                <Button label='Add author' onClick={() => void showAddAuthor()} />
                <DataTableForObservableQuery query={AllAuthors} emptyMessage='No authors yet'>
                    <Column field='name' header='Name' sortable />
                </DataTableForObservableQuery>
                <AddAuthorDialog />
            </Page>
        );
    };
    ```

3. **Try it.** Click **Add author**. The dialog opens with **Add** disabled, because the required name is still empty. Type a name and **Add** enables. Confirm, and the dialog shows its busy state while `RegisterAuthor` executes, then closes.

</Steps>

`useDialog` mounts `AddAuthor` only while the dialog is open, so every click creates a fresh `id`. You didn't wire the buttons either: `CommandDialog` closes itself through the dialog context when the command succeeds, and **Cancel**, the close button, and Escape close it without executing.

<Aside type='caution' title='initialValues, not onBeforeExecute'>
    `CommandDialog` also offers `onBeforeExecute`, which transforms the values just before
    execution. It runs only on submit, after the form has already validated, so a required
    value first set there arrives too late and **Add** never enables. Put every required
    value the user doesn't type — ids, a parent id, the selected row — in `initialValues`.
</Aside>

## Check command success, then the query result

Use a recognizable synthetic name, such as **Sample Author**, so you can find the new row.

1. Open **Add author**, leave **Name** empty, and check that **Add** is disabled. Enter a name; confirm becomes available once client validation passes.
2. Choose **Cancel** once. The dialog closes without executing. Reopen it and submit the name. While execution is pending, the dialog is busy; on success it closes.
3. Watch the table for the new name. It appears when `AllAuthors` delivers the updated result, not because closing the dialog inserts a local row.

A closed dialog and a visible row are different checkpoints. If the command is rejected, the dialog stays open; inspect validation messages or the failed request. If it succeeds but no row arrives, inspect the observable query connection and backend read-model update before submitting again. Retrying a successful registration creates another command with a fresh id, not a refresh.

For a Chronicle-backed application, also check that its projection has updated the queried read model. The table does not provide a write/read consistency or timing guarantee.

<Aside type='tip' title='Validation flows through'>
    Rules the backend shares with the client — like the blank-name `ConceptValidator` from
    [the Arc tutorial's validation chapter](/arc/tutorial/validation/) — are extracted into
    the generated proxy, so `CommandDialog` runs them and keeps **Add** disabled without a
    round trip. Rules that need the database, such as a unique name, run on the server; when
    one rejects the command, the dialog stays open and shows the message against the field.
    Either way you write no frontend validation code.
</Aside>

## Rename and remove are just more commands

Editing isn't a different mechanism — it's another command. The Arc tutorial doesn't define rename or remove commands, but if you add a `RenameAuthor` command with an `id` and a `name`, its dialog follows the same shape. It needs to know _which_ author, so pass the selected author's id and current name as `initialValues`. This excerpt assumes an `author` variable holding the selected row:

```tsx title="Excerpt: a RenameAuthor dialog"
<CommandDialog<RenameAuthor>
    command={RenameAuthor}
    title='Rename author'
    okLabel='Save'
    initialValues={{ id: author.id, name: author.name }}
>
    <InputTextField<RenameAuthor> value={(command) => command.name} title='Name' />
</CommandDialog>
```

A remove command with nothing but the id is often a confirmation rather than a form; pass `initialFocus={DialogInitialFocus.Cancel}` (from `@cratis/components/Dialogs`) so a stray Enter doesn't confirm it. The table reflects these changes when its observable query delivers the updated result. In the next chapter you'll get the selected row from `DataPage` and pass it to a real command from the Arc tutorial, `AddBook`.

## What you built

- An **Add author** dialog generated from the `RegisterAuthor` command, opened with `useDialog`, with its required `id` in `initialValues`,
- a table that renders the subsequent observable result without application refresh code,
- and the pattern for every other change: model it as a command, open it in a dialog, let the list follow.
